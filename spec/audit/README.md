# 全体の確認（監査）の手順

domble が「個人事業主の会計ソフトとして実用に耐えるか」を、まっさらな目で確かめ、足りないところを洗い出すための手順です。何度もくり返すので、手順・分野・書き方をここに決めておきます。結果は日付ごとのファイル（例：`2026-10-28.md`）に残し、直すものは README の「足りていないところ」に移します。

## 基準
- **確定している年分で、帳簿付けから決算書・確定申告（所得税・消費税）まで正しく最後まで扱えるか**を合格の基準にする（2026年10月の確認では令和7年分）
- 次の年分（令和8年分など）は、公表済みの税制改正・様式案の範囲で、違いがあれば添える。年分ごとに決まりを切り替えられる作りかも確かめる
- 対象：ふつうにいる個人事業主（フリーランス・サービス業、在庫のある小売・飲食、建設などの請負、家族を専従者にする事業、従業員を雇う事業、不動産所得、白色申告）。限られた業種（農業・医師の特例など）は「対象にするか決めるもの」に分ける
- 比べる相手は、一般的な市販の個人事業主向け会計ソフトが当然できることと、国税庁の要件。ほかのソフトの製品名・会社名は書かない

## 担当への共通の決まり
- リポジトリは変更しない（読むだけ）。git を操作しない。作業ファイル・スクリプトは scratchpad に置く
- 国税庁（nta.go.jp・e-tax.nta.go.jp・keisan.nta.go.jp）の公式の資料を根拠にする。ファイルをダウンロードするときは、利用者の許可を取ってから
- アプリの画面（ブラウザのプレビュー）は担当ごとには使わない（ぶつかるため）。確かめるときは bun のスクリプトで、DB は `src/db/repo.test.ts` の makeDb と同じく bun:sqlite のメモリ上に作る
- 「誤り」は、テストかスクリプトで再現してから書く。確かめられなければ「要確認」

## 書き方
各担当のファイルは次の3つの節にする。
1. **確かめた項目の一覧（チェックリスト）**：対応済みも含めて全部。`- [判定] 項目名 — 根拠（制度）／ 根拠（コード file:行）`。判定は 対応済み／不完全／未対応／誤り／対象外（理由）
2. **指摘**：対応済み以外を1件ずつ。判定・重さ・制度の根拠（資料名と URL）・コードの根拠（file:行）・内容（具体例）・直し方の案
3. **まとめ**：重さ A・B の件数と、いちばん大事な3点

重さ：
- **A** 申告できない・数字が違う
- **B** 法令の要件を満たさない
- **C** 実務で困る（ふつうのソフトなら当然できる）
- **D** あると良い

## まとめ方
1. 各担当の指摘を読み、重さ A・B のものは自分でコードを開いて裏取りする（担当の書き間違いを残さない）
2. 分野をまたいで同じ指摘はまとめ、重い順に並べた報告を `spec/audit/<日付>.md` に書く。チェックリストは `spec/audit/checklist.md` を更新する（次回はこのリストから始める）
3. README の「足りていないところ」に、直すものを重さつきで足す（すでにある項目は書き直す）。README の「対応の記録」には触れない（直したときに移す）
4. 直す順番を利用者と相談する
