## 指摘

### E-01 保存の途中で止まったあとの自動バックアップが壊れる。バックアップの失敗も知らせない
- 判定：誤り
- 重さ：C
- 制度の根拠：該当なし（運用の安全。電帳法の事務処理マニュアルのひな形が「開くたびに自動で複製する」をバックアップの手順としている：lib/ebook.ts:83-84）
- コードの根拠：src/db/database.ts:40-50（`copyFile` で本体だけを複製。`-journal` は複製しない）、82-91（開く前に複製し、失敗は console.warn だけ）、src-tauri/src/db.rs:95-100（ロールバックジャーナル。WAL ではない）
- 内容：SQLite はトランザクションが大きくなる（既定のキャッシュ 2MB を超える）と、確定する前のページを本体に書き、元の内容を `-journal` に残す。この状態でソフトが止まると、次に開いたときに SQLite が `-journal` で元に戻すが、domble はその**前に**本体だけを複製する。そのため、いちばん新しいバックアップが「書きかけを含む・壊れた」ファイルになる。証憑の取り込み（1件 10MB → base64 で約 13MB）や数千件の CSV 取り込み・明細の登録の途中でウィンドウを閉じる（ログアウトの記録は3秒しか待たない：App.tsx:122）・電源が落ちる、で起きる。
  - 再現（work-E/crash.test.ts。子プロセスで 13MB の証憑を入れるトランザクションの途中に SIGKILL。SQLite の標準どおりキャッシュがいっぱいになったら本体に書く設定）：本体 11.9MB・`-journal` あり → 本体だけの複製は `PRAGMA integrity_check` で「database disk image is malformed」、伝票 No.1 の摘要は書きかけの「TX中の書きかけ」。本体は `-journal` で戻されて ok。
  - また、ディスクがいっぱい・権限が無いなどでバックアップに失敗しても、画面には何も出ない（console.warn だけ）。
- 直し方の案：開いてから（SQLite が `-journal` を戻したあとに）SQLite のバックアップ API（rusqlite の backup。読み取り専用で使っているものと同じ）で複製する。複製のあとに `PRAGMA quick_check` をかけ、失敗やディスクの空きの不足は画面上部で知らせる。

### E-19 仕訳が多いときの性能

- 内容（測定：work-E/perf.test.ts、bun:sqlite・厳密モード・5年で1万件）：

## まとめ
- 重さ A：0 件、重さ B：1 件（E-03：帳簿の印刷と利用者向けの操作説明書が無い。電帳法の見読可能性とシステム関係書類の要件）
- 重さ C：14 件（E-01・02・04〜14・19）、重さ D：4 件（E-15〜18）
- データの安全の土台（トランザクション・古い帳簿の移行・トリガー・連鎖のハッシュの版をまたいだ互換・最近足した表の締め）は、確かめたかぎり壊れていない。過去12版の帳簿の移行、古い版で作った履歴の照合、新しい機能を使ったあとの改ざんの確認は、すべて誤りなく通った。

いちばん大事な3点
1. **バックアップと復元が弱い（E-01・E-02・E-06）**：保存の途中で止まったあとの最新のバックアップは壊れる（再現済み）。失敗しても知らせない。戻す機能が無い。本体と同じフォルダに「開いた回数」ぶんだけ帳簿まるごと残る。暗号化しても前の暗号化していないバックアップが残る。開いたあとに SQLite のバックアップ API で複製して確かめる、「今すぐ・閉じるとき・場所を選ぶ・戻す」を用意する、が先決。
2. **帳簿の印刷と操作説明書（E-03、B）**：電子帳簿として保存する要件（書面に整然と出力・操作説明書の備付け）を、ソフトの機能として満たしていない。domble の画面自身がこれをチェックリストに挙げている。
3. **間違いが黙って帳簿に入る・食い違う（E-04・E-05・E-08・E-09）**：日付の欄に不正な日付を打つと前の日付で登録される（再現済み）。定型仕訳や明細のルールが指す取引先・科目を消すと、登録が「FOREIGN KEY constraint failed」でまとめて失敗する（再現済み）。新しい版の帳簿を古い版で訂正すると用途区分が消える（再現済み）。締めた年度の決算書が固定資産台帳などの変更で変わる（再現済み）。
